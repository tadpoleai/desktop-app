# Hera Desktop 项目分析与重构前记录

> 分析日期：2026-08-03  
> 分支：`feat/laser-panorama-calibration`（`8e29509`）  
> 范围：代码静态分析与现有单元测试；未使用同一批真实采集数据做耗时剖析或画质对照，因此本文区分“代码确认”“高概率判断”和“待实测”。

## 1. 项目定位

Hera Desktop 不应被定位成某一个算法的 GUI，而应是团队算法和数据处理流程的本地集成、验证与交付平台。它当前已经具备四层结构：

1. React/Tauri 提供会话选择、参数配置、任务进度和结果检查；
2. `runner` 负责工作流 DAG、参数注入、容器执行和任务记录；
3. `operators` 将 GLIM、Insta360 MediaSDK、数据导出等团队算法封装成统一契约；
4. `workflows` 组合“输入 → 算法 → 产物”。

对这个定位而言，首要目标应是：同一输入和同一版本得到可复现结果；失败能被准确识别；每个阶段的耗时和质量可以度量；昂贵的中间产物可以安全复用。当前代码已完成“可运行”的骨架，但离“稳定的算法验证平台”仍缺少缓存、产物校验、完整 provenance、质量指标和基准数据集。

## 2. 当前关键处理链路

### 2.1 全景链路

```text
.insv 原始双鱼眼视频
  → panorama-stitch-gpu / MediaSDKTest
     固定 optflow、3840x1920、FlowState=false
  → panorama.mp4
  → frame-extract / ffmpeg
  → panorama_frame.jpg
```

标定首次运行使用 `calib_panorama_frame`，完整拼接后再抽第 0 秒的一帧。后续改变时间点时，UI 已能通过 `calib_frame_extract` 复用 `panorama.mp4`，避免再次拼接。

### 2.2 GLIM 点云/深度图链路

```text
.hera/.db3
  → glim-recon（默认 CPU，window=0.1）
  → GLIM map + traj_lidar.txt + submaps
  → glim-export-pcd
  → 全会话 map_export.ply
  → 世界系按当前 pose 转回 LiDAR 系
  → 方位/俯仰分桶，每桶保留最近点
  → 720x200 伪彩深度图
```

运动场景优先读取时间窗口重叠的 GLIM submap；解析失败或无 submap 命中时，当前实现会静默退回整幅全会话地图。

### 2.3 原始“单帧”深度图链路

```text
.hera
  → storage-extract-mid360 --points
  → 带 timestamp_host_ns 的 CSV
  → 当前时刻 ± window/2 过滤（默认 window=0.8s）
  → 同一套 720x200 最近点分桶和伪彩显示
```

这里的“单帧”实际是 0.8 秒时间窗，而非设备的一帧或一次完整扫描。这是为 Mid-360 非重复扫描在覆盖率和瞬时一致性之间做的折中。

## 3. 问题一：每次全景生成时间较长

### 3.1 已由代码确认的直接原因

1. **首次标定总是处理完整 `.insv`。** `calib_panorama_frame` 把原文件直接交给 `MediaSDKTest`，即使最终只需要一张图，也先生成整段 3840×1920 全景视频。
2. **默认使用 `optflow`。** manifest 已说明它质量最好但不是最快；当前标定工作流将其固定，无法针对“只做标定抽帧”选择更轻的执行策略。
3. **工作流没有内容寻址缓存。** 每个 job 使用新 UUID 输出目录；Runner 不检查相同输入、算子版本、参数是否已有有效产物，所以重复进入流程会重新拼接。
4. **已有复用只发生在同一次 UI 会话中。** `CalibrationView` 能拿当前 job 的 `panorama.mp4` 做重新抽帧，但任务历史中的旧产物没有作为可复用依赖被自动解析。
5. **无法用数据回答“慢在哪”。** Runner 只记录 job 起止时间，未记录 step 起止时间、输入大小、GPU 型号/利用率、解码/拼接/编码阶段耗时，也没有解析 MediaSDK 的进度或性能指标。
6. **曾尝试用 ffmpeg 裁剪失败是格式约束，不代表只能全量计算。** 当前注释确认重新封装会丢失 Insta360 私有镜头标定元数据；因此不能简单恢复 `ffmpeg -c copy`，但仍可研究 MediaSDK 自身的帧区间/单帧接口，或保存原始元数据的裁剪方式。

### 3.2 高概率瓶颈排序

在没有实测 profile 前，建议按以下顺序验证，而不是直接改参数：

1. 完整视频的光流拼接，耗时大概率随视频时长近似线性增长；
2. 4K H.264 输出编码和磁盘写入；
3. 容器冷启动、镜像检查和 GPU 初始化；
4. 输入文件挂载/读取性能，尤其是 Windows Docker Desktop 或网络盘；
5. 后续 ffmpeg 抽帧通常只占较小部分。

### 3.3 建议方案

**P0：先量化。** 为每个 step 增加 `queued/start/end/duration`，记录输入字节数、输出字节数、operator 版本/digest、实际合并后的参数和运行设备。准备短/中/长三段固定 `.insv`，各跑冷启动与热启动三次。

**P0：增加可靠缓存。** 缓存键至少包含：输入文件内容指纹（大文件可用 size + mtime + 分块 hash，最终质量基准用完整 hash）、operator image digest、展开后的实际参数、工作流/算子契约版本。命中后仍需校验产物存在、非空且可解码。

**P1：拆分“标定抽帧”和“全景视频生产”。** 标定只需要一帧，不应天然依赖完整视频产物。优先确认 MediaSDK 是否支持按时间范围或指定帧拼接；若不支持，再把“一次完整拼接、多次复用”作为显式会话资产，而不是临时 job 产物。

**P1：提供经过验证的速度/质量档位。** 例如 `calibration-fast` 与 `production-quality`，但必须在相同标定数据上比较接缝偏差和特征位置误差后再决定是否允许 template/dynamicstitch；不能只看肉眼观感。

**不建议立即做：** 再次用普通 ffmpeg 重封装 `.insv`；降低分辨率或切换拼接算法而不测量标定点位偏差；仅靠 UI 保存某个 job 路径作为缓存。

## 4. 问题二：GLIM 和单帧模式的深度效果均不理想

### 4.1 先区分“点云质量”和“深度图观感”

两种来源都经过同一个 `build_range_image`。因此“两种模式都不好”首先指向公共的可视化/分桶环节，而不能直接得出 GLIM 重建质量差。应分别评估：

- 点云本身：坐标、时间、漂移、离群点、密度；
- 深度栅格：角度映射、遮挡选择、空洞率；
- 颜色显示：距离归一化、动态范围、空洞颜色；
- 与全景对齐：外参和时间同步。

### 4.2 公共深度图层的确定问题

1. **用全局最小/最大距离线性着色，极易压缩主体对比度。** 一个极近噪点或极远离群点就会占据色带两端，让主要场景落在很窄的颜色范围。这是当前“深度层次不明显”的首要代码级嫌疑。应改用有效深度的稳健百分位（如 P2–P98）、可配置米制范围，或对数/逆深度显示；原始米值仍保留用于选点。
2. **俯仰范围由样本 min/max 自动拟合，同样会被离群点拉伸。** 现有修复解决了固定 ±90° 导致大量灰区的问题，但应进一步用分位数或已知 Mid-360 FOV，并将被裁剪点数作为指标显示。
3. **720×200 共 144,000 个 bin，最近点策略不做补洞。** 0.8 秒原始数据约 160k 点并不等于 160k 个独立角度 bin；非重复扫描和遮挡会造成大量重复/空洞。当前灰色空 bin 会让图像显得破碎。
4. **每 bin 只保留最近点。** 这是合理的可见面近似，但对飞点、车体/支架近点非常敏感；一个近距离噪点会覆盖正确表面。需要最小距离过滤、离群过滤，或按 bin 使用小样本中位数/置信度。
5. **深度图输出缺少诊断量。** 目前只有占用 bin 数和 min/max；还应输出 occupancy、距离分位数、被过滤点数、每 bin 冲突数、时间窗内点数，才能判断是数据稀疏还是显示失真。

### 4.3 原始“单帧”模式特有问题

1. **0.8 秒是经验常量，不是真正单帧。** 静态场景可提高覆盖，运动场景会产生运动拖影；窗口越大，深度越完整但几何越不瞬时。
2. **仅按 `timestamp_host_ns` 过滤，没有逐点运动补偿。** 运动期间窗口内所有点仍按 LiDAR 原始坐标直接叠加；若载体移动或转动，0.8 秒足以造成结构增厚、重影和边缘模糊。
3. **CSV 每次全文件读入字符串并逐行拆分。** 这主要影响交互性能和内存稳定性，也妨碍快速迭代窗口。应使用流式/索引读取，或预生成二进制时间索引。
4. **静态分支会使用整段原始 CSV。** 即使设备不动，动态物体和长时间噪声都会被累计；它并非严格单帧。

建议将“单帧原始”改名为“原始时间窗”，并提供两种明确模式：短窗原始（高瞬时性）与逐点运动补偿后的累积窗（高覆盖率）。

### 4.4 GLIM 模式特有问题

1. **GLIM submap 过滤粒度粗。** 当前只能按 submap 的帧时间范围决定整块加入，而一个 submap 可能覆盖数秒或数百帧；即使 UI 选择 0.8 秒，实际进入深度图的点仍可能远超该窗口并包含其他视角。
2. **解析依赖逆向工程格式。** `data.txt` 和 `points_compact.bin` 没有上游稳定契约；解析失败时 submap 被静默跳过，UI 侧又会静默退回全会话地图。这会把数据契约错误表现成“深度效果不好”。应显式报告 fallback 原因和实际数据源。
3. **整幅 map fallback 会混合全会话视角。** 转换到某一时刻 LiDAR 坐标系并不能撤销其他时刻观测的动态物体、漂移和遮挡关系，因此会出现重影/穿透/杂乱。
4. **重建参数未形成受控配置。** 默认 CPU、`window=0.1`、OVERLAP；静态模式可覆盖成 DISPLACEMENT，但缺少按数据特征选择参数的基准。GLIM 的 IMU 外参、安装方向、噪声和时间同步任何一项错误都会降低地图质量。
5. **`exit 139` 被当成成功。** `glim-recon` manifest 接受 `[0,139]`，这是历史上绕过清理阶段崩溃的兼容措施。Runner 又不校验输出目录/轨迹/子图是否完整，因此截断或不完整地图可能被登记为成功产物，直接违背“稳定性优先”。

优先方案是让 GLIM 导出带 point/frame timestamp 的受支持格式，或在生成 submap 时保留 point→frame 关系；如果短期不能修改 GLIM，至少不要静默 fallback，并在 UI 展示“实际使用了 N 个 submap、覆盖时间范围 X、点数 Y”。

### 4.5 时钟与坐标系风险

当前代码注释已明确：`traj_lidar.txt` 与 CSV host clock 的关系只在一份真实会话上做过 spot check；Mid360 与 Insta360 的精确换算还依赖同步检测结果和首个点的 host timestamp。时钟误差主要表现为与全景对不上，坐标轴/倒置配置错误则会表现为上下翻转或结构方向异常。这两类问题不应通过调色或加大时间窗掩盖。

应建立自动检查：时间范围重叠、首尾 offset、轨迹单调性、相邻 pose 速度上限、重力方向、LiDAR FOV 统计，以及已知平面/标靶上的投影误差。

## 5. 稳定性优先下发现的编排层风险

这些问题不一定直接造成当前两个现象，但会让后续算法验证结论不可信：

1. Runner 在 step 退出码通过后不校验声明的 output 是否存在、非空、格式可读。
2. provenance 记录的是 `node.params`，不是合并用户 override 后真正执行的参数，导致实验不可复现。
3. `latest` 算子解析依赖 registry 的 `added_at`；工作流多数没有 pin 版本/digest，同一工作流可能随本机注册状态变化。
4. DAG 拓扑排序不对环、未知节点、缺失输入做严格失败；契约校验不足。
5. 没有 step 级指标、质量门禁、重试策略、超时和资源记录。
6. 大文件深度图读取与重建没有中间索引/缓存，每次时间轴刷新可能重复扫描和分桶。
7. manifest 同时维护 `params_schema/params_bindings` 和旧 `params` 两套定义，存在漂移风险。

## 6. 建议的验证顺序

### 阶段 A：建立可重复基线（先做）

- 固定 3–5 个脱敏样例：静态室内、静态室外、低速运动、快速转动、含动态物体；同时保留 `.hera/.insv/.session.json`。
- 固定 operator image digest 和 GLIM config 快照。
- 每次运行记录 step 耗时、输入输出 hash/大小、实际参数、设备信息。
- 深度质量最低指标：occupancy、P2/P50/P98 深度、有效 FOV、离群率、平面厚度、连续帧一致性。
- 全景指标：总耗时、实时率、输出帧数、接缝区域特征位移、目标帧可解码性。

### 阶段 B：低风险修正

- 深度着色采用稳健分位数，并显示可调深度范围。
- 显式展示空洞率、实际时间窗/实际 submap 范围和 fallback 状态。
- 加输出验证；逐步取消无条件接受 GLIM 139，至少要求核心产物完整。
- provenance 保存实际参数，工作流 pin 版本/digest。
- 对全景产物做会话级缓存和完整性校验。

### 阶段 C：算法改进

- 原始点云增加逐点运动补偿和时间索引。
- GLIM 提供细粒度带时间点云导出，不再依赖 submap 粗筛。
- 深度图增加近点屏蔽、统计滤波、可选补洞；注意补洞只用于显示，选点必须能追溯到真实点。
- 评估 MediaSDK 指定帧/时间段能力；没有可靠接口时保留完整拼接但强化缓存。

## 7. 重构方向

建议围绕“可复现的处理资产”重构，而不是按页面重写：

```text
Session Asset
  ├─ Raw streams + clock model
  ├─ Panorama asset (versioned, cached, validated)
  ├─ Point-cloud asset (frame + timestamp semantics explicit)
  ├─ Trajectory asset
  └─ Calibration asset
          ↓
Typed Operator Contract
  input/output schema + version/digest + validator + metrics
          ↓
Execution Engine
  cache key + resource scheduling + timeout/retry + provenance
          ↓
Workflow / Experiment
  pinned graph + parameter set + quality report + comparison
```

核心数据类型必须显式携带：坐标系、时间域、时间范围、是否运动补偿、单位、来源算子及版本。当前大量语义只存在于注释和文件名中，这是下一轮重构最应消除的隐患。

## 8. 本次结论

- 全景慢的首因不是 Tauri 或 DAG，而是“为一张标定帧完整执行全视频 optflow 拼接”，再叠加缺少跨 job 缓存和耗时观测。
- 两种点云模式都觉得深度差，公共首因优先检查深度图表达：min/max 线性色带、离群点驱动的自动 FOV、144k 栅格空洞和最近点噪声；不能先归咎于 GLIM。
- 原始模式的核心矛盾是非重复扫描覆盖率与运动拖影；GLIM 模式的核心矛盾是 submap 时间粒度过粗及静默退回整图。
- 在继续调算法前，应先修复产物校验、实际参数 provenance、版本 pin 和质量指标，否则每次实验结果都难以复现和比较。

## 9. 已完成验证与待补证据

本次执行 `cargo test -p hera-runner`：31 个测试全部通过，覆盖现有 range image 自动俯仰拟合、窗口过滤、submap 变换、轨迹插值和标定数学。它们证明局部数学实现与当前假设一致，但没有覆盖真实设备数据质量、MediaSDK 耗时、GLIM 139 产物完整性、时钟域一致性和端到端画质。

下一次进入实现前，最有价值的输入是：一组问题样例的 `.hera/.insv/.session.json`、两种模式的截图、对应 job 日志和机器/GPU 信息。用同一数据做基线后，才能判断每项修改究竟改善了算法、显示，还是只改变了观感。

## 10. 标定交互补充结论（2026-08-03）

- 360 叠加预览在 Ubuntu/WebKitGTK 中无法拖动，不是球面投影问题，而是 pointer capture 后 `movementX/movementY` 可能恒为 0。交互必须用相邻 `clientX/clientY` 自行计算位移，并处理取消捕获。
- 0802 实测原始点云 CSV 约 1.88 GB。时间轴每次刷新若整文件读成字符串，会同时造成长等待和明显内存峰值；时间窗读取应流式扫描，并在时间戳超过窗口上界后提前结束。
- 原始时间窗原默认 0.8 s，运动场景会把多帧扫描直接叠在雷达坐标系，产生边缘拖影。第一阶段默认改为 0.2 s（仍可手工增大）；后续若需同时兼顾密度，应基于轨迹做逐点去畸变，而不是继续放大窗口。
- GLIM 的 `points_compact.bin` 是子图聚合点，不带逐点时间戳；当前只能按 `data.txt` 中子图的帧时间范围筛选。一个子图可能覆盖数秒，窗口值不等价于严格逐点切片。后续重构应额外导出点的时间或帧归属，才能实现精确 GLIM 时间窗。
